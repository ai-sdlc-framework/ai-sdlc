## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
**Context.** On 2026-10-11 the AISDLC-667.1 pipeline stopped before review because `pnpm test` failed 4 cases in `pipeline-cli/src/cli/bin-invocation.test.ts` and 3 in a `verify-runtime.test.ts`. The diff touched neither file. The same 4 `bin-invocation` cases fail on a clean main checkout on the operator machine after a fresh `pnpm install --frozen-lockfile` (pnpm 9.15.4, Node 22.23.2). Every pipeline run in that state is blocked.

**bin-invocation cause.** The describe `AISDLC-156 + AISDLC-181: bin invocation pattern (CI cost-saver + umbrella bin guard)` contains a `describe.each(ALL_GUARDED_BINS)` named `` `pnpm --filter @ai-sdlc/pipeline-cli exec %s` STILL FAILS `` (around line 183), each with one case named `— defense against future workflow regressions reverting to the broken pattern`. Rendered names include `` `pnpm --filter @ai-sdlc/pipeline-cli exec cli-classify-pr` STILL FAILS ``, and the same for `cli-incremental-decide` and `cli-classify-budget` plus the remaining guarded bin. Each spawns `pnpm --filter @ai-sdlc/pipeline-cli exec <bin> --help` from the workspace root and asserts a non-zero exit. After a fresh install `pnpm exec cli-classify-pr` now SUCCEEDS, so the assertion `pnpm exec <bin> unexpectedly succeeded — re-evaluate AISDLC-156/181` fires. Whether `pnpm exec` resolves a workspace's own bins depends on `node_modules/.bin` linking state, not on repository code, so the test is environment-dependent.

**verify-runtime note.** The task-filing request named `pipeline-cli/src/next-step/verify-runtime.test.ts`; that path does not exist. The real file is `pipeline-cli/src/attestation/verify-runtime.test.ts` (AISDLC-575). It is partly hermetic (mkdtemp fixtures, a copied module for the walk-up cases) but the first describe calls `loadAttestationRuntime` in process, and its candidate list includes a `node_modules` walk-up from the module's own on-disk location (`verify-runtime.ts`). So cases such as `fails closed with adopter-actionable guidance when no trusted runtime exists anywhere`, `rejects a candidate that resolves inside repoRoot...` and `rejects an installed copy older than the minimum version...` can change result depending on whether the checkout's own `node_modules/@ai-sdlc/orchestrator` (and its `dist/runtime/attestations.js`) is linked or built. That is a hypothesis to confirm by reproduction, not a finding.

**Five-step review (requirements first).**
1. Requirement (AISDLC-156/181): "workflows invoke pipeline-cli bins via `node pipeline-cli/bin/cli-X.mjs`, never `pnpm --filter ... exec`". The rule is real and is enforced by the positive half, `workflow files invoke guarded bins via direct-node form (AISDLC-181)`, which scans workflow files. The negative half ("pnpm exec STILL fails") is a claim about pnpm behaviour, not a control, and it is wrong on some machines.
2. Delete: the four negative cases (the whole `STILL FAILS` describe.each) and any helper only they use.
3. Simplify: keep the workflow-pattern assertions as the single enforcement. If `.ai-sdlc/gates.yaml` exists (AISDLC-805), add the rule to that gate registry entry's property text; if it does not exist yet, skip that and say so in the PR. Diagnose the verify-runtime failures: reproduce in a fresh worktree under Node 22.23.2; if they depend on `dist`/build or workspace link state, make them build-independent (inject the resolver's start directory or candidate roots) or move them behind the build.
4. Accelerate: none. 5. Automate: none.
