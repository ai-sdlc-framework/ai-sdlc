## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The dark-code gate finds modules nobody imports. It cannot see a module that is
imported and handed a stub, which is how `createPipelineLLMEvaluator()` returns
`createStubLLMEvaluator([])` in production code. This task adds a second rule to the
same script. RFC-0049 section 9.6.

## Conventions for this series
- Design source: `spec/rfcs/RFC-0049-system-one-judgment-layer.md`, section 9. Its Open
  Questions are resolved; do not edit that section. If the RFC and this task disagree,
  stop and return `prUrl: null` with a note naming the conflict.
- TypeScript strict, ESM, `.js` import extensions, 80% line coverage on new code.
  Scripts under `scripts/` use `node --test`.
- Every new module is reachable from a non-test importer or a barrel re-export, so the
  dark-code gate passes (`pnpm dark-code:check`).
- Strings an adopter can see (errors, CLI output, templates) carry no internal task ids.

## Scope
1. **Rule** in `scripts/check-dark-code.mjs`, run over the same source roots and with
   the same comment stripping and specifier resolution as the existing rule. A
   *stub site* is a non-test source file that either:
   - imports from a module whose basename matches a test-double pattern
     (`fake-*`, `*-fake`, `mock-*`, `*-mock`, `stub-*`, `*-stub`, or a `__mocks__` or
     `__test-helpers__` directory), or
   - imports or calls an exported identifier matching `createStub*`, `createFake*`,
     `createMock*`, `Fake*`, `Mock*` or `Stub*`.
   The patterns live in one exported constant so they can be reviewed in one place.
   A file that only defines such an identifier is not a stub site; a barrel that only
   re-exports it is not a stub site.
2. **Allowlist:** `.ai-sdlc/dark-code-baseline.json` gains `stubAllowlist`, entries of
   the form path, capability id and reason, for legitimate uses (for example a mock
   spawner selectable by an explicit command-line option).
3. **Baseline:** the same file gains `stubSites`, the stub sites present when this rule
   lands. The gate fails only on a stub site that is in neither list, reports baselined
   sites that have gone, and refuses growth of `stubSites` relative to the base ref,
   exactly as the dark-module baseline behaves. `--update-baseline` may only shrink it.
4. **Initial baseline:** generated by running the rule on the tree as it stands. The
   stub evaluator call in `orchestrator/src/policy-evaluators.ts` is expected to be in
   it, recorded against capability `policy.llm-evaluator`.
5. **Output** for a new stub site names the importing file, the imported identifier or
   module, and the two ways to resolve it: wire a real implementation, or add an
   allowlist entry with a capability id and reason. `--json` includes stub findings.
6. **Known blind spot**, stated in the script header and in the failure text: an
   interface with no implementation at all has nothing to import and is not detected
   here; that case is covered by capability outcome reporting.
7. **CLAUDE.md:** extend the existing dark-code gate paragraph with two sentences on
   the second rule. Edit in place; add no new section.

## Acceptance Criteria
- [ ] A fixture where production code imports a `fake-*` module fails the gate, and the same import from a test file does not.
- [ ] A fixture where production code calls a `createStub*` export fails the gate; a file that only defines it, and a barrel that only re-exports it, do not.
- [ ] An import that appears only inside a comment is not counted.
- [ ] An allowlist entry with a capability id and reason suppresses the finding; an entry without a reason is rejected.
- [ ] Adding an entry to `stubSites` by hand relative to the base ref fails the gate; removing one that is no longer a stub site is reported and accepted.
- [ ] The committed baseline is exactly what the rule produces on the current tree, and it includes the stub evaluator call under `policy.llm-evaluator`.
- [ ] The existing dark-module behaviour and its tests are unchanged.
- [ ] The failure text and script header state the blind spot.
- [ ] `pnpm build && pnpm test && pnpm lint && pnpm format:check` pass, including `pnpm dark-code:check`.
