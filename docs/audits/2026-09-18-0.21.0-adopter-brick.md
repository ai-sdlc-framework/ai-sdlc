# Post-mortem: the 0.21.0 adopter-brick (AISDLC-562 / #970)

**Date:** 2026-09-18
**Severity:** High — bricked the review → attestation → merge pipeline for every
consumer/adopter repo on plugin 0.21.0.
**Fix:** AISDLC-623 (#1080, behavioral fix) + AISDLC-624 (#1079, related doctor
false-positive). Prevention: AISDLC-625/626/627/628.
**Author:** Dominique Legault

## Impact

In a consumer/adopter repo running plugin **0.21.0**, all reviewer subagents
hard-refused at their first step (`review refused: cannot attribute this run to a
task`) **before reading the diff**. Because a code PR needs a signed attestation
to go green, and an attestation needs reviewer transcripts, "no reviews" meant
"no attestation" meant **nothing could reach green + merge**. The only adopter
workaround was pinning back to 0.20.2. Detection came from a human adopter, not
from our CI, roughly a day after the release.

## Root cause — three compounding causes

The regression originated in **#970 (AISDLC-562)**, which changed reviewer
transcript attribution from **fail-soft** (0.20.2 wrote a shared `UNKNOWN/` dir)
to **fail-closed** (refuse the review). Three things combined:

1. **A trust gate placed in the wrong layer.** The real defect #970 fixed was
   narrow: two unattributed runs writing the *same shared* `UNKNOWN/` directory
   could clobber each other's evidence. But the fix made the **reviewer refuse
   to analyze** — when the collision concern only ever applied to the
   **transcript artifact**, never to the analysis. The review's value (finding
   bugs) never depended on task attribution at all.

2. **The referenced script was never shipped to adopters.** #970 created
   `scripts/resolve-transcript-task-id.sh` but did not add the bundled copy at
   `ai-sdlc-plugin/scripts/`. Plugin scripts are manually duplicated (only a
   couple live in both trees, each with a hand-written parity gate), and no gate
   asserted that a script a reviewer prompt references is actually in the bundle.
   Adopters got `exit 127`.

3. **The reviewer prompt hardcoded a repo-root path.** Every reviewer `.md` ran
   `bash scripts/resolve-transcript-task-id.sh` — repo-root-relative. Even had
   the script been bundled, that path would not resolve in an adopter repo.
   Combined with (2): `exit 127` → the fail-closed branch → refusal.

## Why our own pipeline never caught it

**The monorepo cannot reproduce the adopter environment by construction.** Every
path we exercise has attribution: the resolver script exists at repo root, and
`/ai-sdlc execute` always writes the `.active-task` sentinel. So the fail-closed
branch is never reached in our CI. Compounding that:

- **#970 shipped 327 lines of tests that validated the wrong thing.** Its five
  `describe` blocks tested the script's *internal logic* assuming it exists at
  repo root; the `no-sentinel` block asserted the **refusal was correct** — the
  tests codified the regression as intended behavior. There was zero coverage
  of: script-absent, plugin-relative resolution, or a consumer-shaped dispatch.
- **No bundle-parity gate** asserted the bundle contained the script the prompt
  referenced (a pattern that already existed for other scripts, but wasn't
  mirrored here).
- **No `doctor` check** for the resolver.
- **No adopter/consumer/e2e CI job** exists at all. The first "adopter" to run
  the released bundle in a consumer repo was a human.

## The deeper pattern

Every one of these is the same failure family: **a shared surface changed, but
not all of its consumers or environments were updated or covered.** The pattern
recurred *while shipping the fix*: AISDLC-624 changed a shared script
(`check-stale-runtime-deps.mjs`, switched to `npm view --json`) and broke a
sibling consumer's test (`install-runtime-deps.sh`), whose fake-`npm` stub still
emitted the old plain format — caught only because full-suite CI happened to
cover it, not by the targeted tests that shipped with the change.

## Prevention (filed and shipped)

| Item | What | Closes which gap |
|---|---|---|
| **AISDLC-623** | Fail-soft to a *unique* `UNKNOWN-<reviewer>-…` id; bundle the script; portable path resolution; `doctor` check | Cause 1, 2, 3 (behavioral) |
| **AISDLC-625** | Adopter-environment reviewer smoke test in CI | "monorepo can't reproduce adopter env" |
| **AISDLC-626** | Generalized reviewer-script bundle-parity gate | "no gate asserted the bundle contains it" |
| **AISDLC-627** | "Changing a shared surface" contributor checklist | "tests validated only the in-repo path" |
| **AISDLC-628** | This post-mortem + the fail-soft-at-the-adopter-boundary principle | "trust gate in the adopter's critical path" |

## Lessons

1. **Test the boundary, not just the unit.** A change to a shared surface must be
   tested in the *absent/degraded* consumer environment, not only the in-repo
   happy path. See [CONTRIBUTING.md → Changing a Shared Surface](../../CONTRIBUTING.md#changing-a-shared-surface--test-the-boundary-not-just-the-unit).
2. **Trust gates belong at the artifact boundary, never in the adopter's core
   loop.** See [fail-soft at the adopter boundary](../operations/fail-soft-at-the-adopter-boundary.md).
3. **A green pipeline that can't reproduce the failure environment is not
   evidence of safety.** Our attestation + 3-reviewer + full CI were all green
   on a change that bricked every adopter.
